# Скіли Claude для українського письма

**Українська** · [English](README.en.md)

Два плагіни для Claude, які допомагають писати українською так, щоб текст не
був схожий на переклад чи на машинний текст: без кальок, канцеляриту й
ШІ-кліше. Технічний плагін має сім скілів, художній — один. Можна встановити
один плагін або обидва.

| Плагін | Для чого |
|---|---|
| `ukrainian-tech-docs` | Технічна документація — диспетчер і шість скілів: письмо, перевірка мови, фактчекінг, вивантаження, планування, мультиагентна рецензія. Контракт роботи перед письмом, дисципліна джерел і маркерів невизначеності, жива мова, жанрові правила (HLD, LLD, ADR, ТЗ, how-to і runbook, concept, reference, troubleshooting, постмортем, схема, план), питання до суміжних команд, вивантаження в .docx, .xlsx, .pdf чи лист. Що дати на вхід — [docs/ukrainian-tech-docs-inputs.md](docs/ukrainian-tech-docs-inputs.md); що таке кожен жанр і як його попросити — [docs/ukrainian-tech-docs-genres.md](docs/ukrainian-tech-docs-genres.md) |
| `ukrainian-fiction` | Художня проза — диспетчер і шість скілів: письмо, будова сцени й глави, ідеї сцен, аудит і чистка, читацький тест, налаштування книги й картки героїв. Мова без кальок і ШІ-кліше, правопис і милозвучність, речення і абзац, діалог, будова сцени й глави, аудит готового тексту. Годиться і для перевірки вже написаного тексту — власного чи згенерованого. Правила конкретної книги (герої, словник, лор, тон) пакет не тримає — їх має давати профіль книги |

## Швидкий старт

**Claude Desktop або claude.ai.** Відкрийте чат (не вкладку Code), далі
«Персоналізація» → Плагіни → «Додати» → додати маркетплейс
`alexgorby/claude-skills`, потім «Додати» біля потрібного плагіна.

**Claude Code:**

```
/plugin marketplace add alexgorby/claude-skills
/plugin install ukrainian-tech-docs@alexgorby-skills
/plugin install ukrainian-fiction@alexgorby-skills
```

Далі просто пишіть українською: «напиши ADR про …», «почисти текст»,
«перевір факти», «план готовий». Потрібний скіл вмикається сам. Подробиці,
оновлення й Codex — у розділі [Встановлення](#встановлення).

## Як це виглядає

> **До:** Варто зазначити, що резервне копіювання відіграє ключову роль
> у забезпеченні надійності інфраструктури. Здійснення резервного копіювання
> відбувається щоночі за допомогою скрипта `backup.ps1`, що дозволяє мінімізувати
> ризики втрати даних. Таким чином, наше рішення є надійним, масштабованим
> і гнучким.
>
> **Після:** Резервну копію щоночі знімає скрипт `backup.ps1`.
>
> **Питання до автора:** скільки даних можна втратити за такої схеми (RPO)
> і скільки триває відновлення? Речення про надійність прибрано, бо в ньому
> не було факту.

Кожна знахідка має номер пункту правил: `1.1 · S1` — підводка, `1.2 · S2` —
віддієслівний іменник, `1.9 · S2` — примусова трійка. Повний розбір цього
абзацу й аудит художнього уривка — у [docs/examples.md](docs/examples.md).

## Що вміє

Потрібний скіл вмикається сам, коли запит схожий на один із наведених. Формулювання
не обов'язково повторювати дослівно.

### ukrainian-tech-docs

Пакет має шість скілів, кожен робить одну задачу. Запит на кілька задач одразу
(«підготуй документ для Замовника») розводить диспетчер: каже, які скіли
потрібні та в якому порядку.

| Що зробити | Як попросити | Скіл |
|---|---|---|
| Написати документ потрібного жанру | «Напиши ADR про вибір …», «покрокова інструкція для …», «ТЗ на …» | `write` |
| Переписати документ, оформити нотатку | «Перепиши документ», «оформи як нотатку» | `write` |
| Перекласти технічний текст | «Переклади українською» | `write` |
| Сформулювати питання до суміжної команди | «Сформулюй питання до мережевиків про …» | `write` |
| Почистити текст від ШІ-кліше, канцеляриту й кальок, не чіпаючи змісту | «Почисти текст», «прибери воду» | `language` |
| Знайти кальки, нічого не правлячи | «Діагностика кальок», «перевір переклад» | `language` |
| Перевірити готове ТЗ | «Перевір ТЗ» | `language` |
| Звірити твердження з документацією | «Фактчекінг», «перевір факти», «звір із документацією» | `factcheck` |
| Зібрати файл для читача поза командою | «Збери docx», «оформи як лист» | `export` |
| Скласти план роботи | «Спершу план», «склади план» | `plan` |
| Незалежно перевірити план чи документ | «План готовий», «перевір незалежно», «рецензія HLD» | `review` |
| Перевірити, чи зрозуміло без автора | «Тест читача», «чи зрозуміло це без мене» | `review` |

Рецензія `review` дає план чи документ кільком вузьким рецензентам-агентам:
узгодженість, здійсненність, опонент рішень, безпека, архітектура, мережа
тощо. Рецензентів вибирає окремий агент-координатор, і кожен бачить лише сам
предмет, а не розмову, у якій його склали. Знахідки щодо документа ще перевіряє
опонент, головна сесія звіряє кожну з джерелом. Де субагентів немає, рецензія
йде в одній сесії і позначається як «не незалежна».

**Жанри.** Для кожного — свої правила будови й власний чек-лист.

| Жанр | Що в ньому |
|---|---|
| HLD | Концепції, рішення, компроміси, без значень конкретної збірки |
| LLD | Значення, адреси, параметри й порядок кроків як наслідок рішень HLD |
| ADR | Одне архітектурне рішення з варіантами й компромісом |
| ТЗ | Що потрібно і як це приймають: лише виконувані пункти, без відкритих питань |
| How-to, runbook, процедура | Кроки з перевіркою та відкатом |
| Покрокова інструкція | Лише дії для читача, який їх ще не виконував: пререквізити з перевіркою, крок за кроком |
| Concept | Як працює компонент |
| Reference | Таблиці, схеми даних, коди, без прози |
| Troubleshooting | Запис випадку, симптом першим |
| Постмортем | Закриття інциденту після відновлення сервісу |
| Безпековий документ | Як система захищена: доступ, секрети, мережева поверхня, дані, ланцюг постачання |
| Схема | Топологія і механізм, читаність у друці |
| План | Лише коли попросите: «спершу план», «склади план» |
| Лист, повідомлення, нотатка, README | Загальні правила: один документ — одне завдання; лист — зріз робочого документа для одного адресата |

Докладно про кожен жанр і як його попросити —
[docs/ukrainian-tech-docs-genres.md](docs/ukrainian-tech-docs-genres.md).

## Скіли докладно

Приклади взято з
прогонів 02.11.2026 на синтетичних текстах (умовний продукт «Ліхтар», вигадані
нотатки); відповіді скорочено, пропуски позначено «…».

### Диспетчер — `ukrainian-tech-docs`

Вмикається, коли запит охоплює кілька задач одразу або незрозуміло, який скіл
брати. Каже, які скіли потрібні, у якому порядку й чому. Сам нічого не пише:
роботу роблять скіли, які він назвав. Неоднозначні запити розводить таблицею:
«переписати документ» — письмо, «почисти текст» — мова, «перевір ТЗ» — аудит
ТЗ, тип тексту не названо — одне питання власникові.

**Запит:** «Підготуй для Замовника документ із цієї чернетки HLD, треба docx:
"Сервіс черги «Ліхтар» працює у двох вузлах. Повідомлення зберігаються 7 днів."
Нічого не збирай — лише скажи, які кроки й у якому порядку».

> 1. **Письмо (`write`).** Чернетка — два речення, а Замовнику потрібен HLD.
>    Спершу контракт роботи… Нічого не домислюю: чого в чернетці немає, те
>    стає маркерами невизначеності й питаннями. Наприклад: що таке «вузол» —
>    ВМ, фізичний сервер чи под? Це active/active чи active/passive?
> 2. **Фактчекінг (`factcheck`)** — лише якщо з'являться твердження про
>    вендора, ліміти чи версії…
> 3. **Рецензія (`review`)** — не запускаю без вашого слова… Запропоную її
>    після кроку 1, бо документ іде Замовнику.
> 4. **Вивантаження (`export`) у .docx.** Останній крок, і він починається з
>    повного мовного проходу по остаточному тексту…
>
> Питання: спершу показати перелік відкритих питань до чернетки чи писати
> документ одразу з маркерами на місці прогалин?

### Письмо — `write`

Пише й править документ будь-якого жанру: HLD, LLD, ADR, ТЗ, runbook,
покрокову інструкцію, постмортем, лист, нотатку, переклад, схему, питання до
суміжної команди. Робота йде так:

- **Контракт** — до першого рядка тексту сім рядків: жанр, читач, чи йде
  документ назовні, межа глибини (що лишається в HLD, а що йде в LLD), звідки
  наповнення, чого не робимо, які стадії пройде робота. Заперечення міняє
  рядок.
- **Профіль проєкту** — один файл у вашому проєкті, з якого скіл бере словник,
  реєстр кодів, сходи джерел, місце реєстру питань. Профілю немає — скіл каже
  про це й не вигадує вмісту.
- **Джерела** — кожне твердження про платформу має адресу джерела там, де
  стоїть. Чого немає в джерелах, того немає в тексті: замість цього маркер
  невизначеності або питання.
- **Вилки й питання** — коли рішення не за автором тексту, скіл дає варіанти
  із ціною кожного, адресата й рекомендацію.
- **Самоперевірка** — чек-лист жанру, фінальний мовний прохід, перелік
  тверджень без джерела, підсумок маркерів і рядок стадій.

Планування вмикається лише на ваше прохання, письмо його не пропонує.

**Запит:** «Напишіть короткий фрагмент HLD за записом D-02 реєстру кодів.
У цьому HLD RPO 15 хв лишається в тілі».

> **Контракт роботи**
>
> | Рядок | Значення |
> |---|---|
> | Жанр | HLD, фрагмент розділу |
> | Межа глибини | Концепції: рішення, ціль, компроміс. Виняток із межі: у цьому HLD значення RPO 15 хв лишається в тілі… Інтервали, параметри та команди йдуть у LLD |
> | Звідки наповнення | `codes.md`: запис D-02 прочитано повністю… |
> | … | … |
>
> **Асинхронне копіювання і ціль RPO**
>
> Обрано асинхронне копіювання. Ціль RPO — 15 хв… Рішення має ціну: у разі
> аварії можуть бути втрачені зміни, які ще не скопійовано… Чи виконується ця
> умова, невідомо: вимірів фактичного досягнення RPO немає.
>
> **1. Чи міряти фактичне відставання копії.** А — виміряти на стенді… Б —
> лишити «вимірів немає»… Адресат — власник стенда. Рекомендую: А — без виміру
> ціль RPO лишається побажанням, а не перевіреною властивістю.
>
> Перелік тверджень без джерела: немає… Підсумок маркерів: маркерів не ставив.
>
> `Стадії: вхід (… genres/hld …) · письмо (evidence, language, genres/hld) · вилка (forks-and-questions) · самоперевірка (чек-лист hld, … фінальний прохід language …)`

### Перевірка мови — `language`

Перевіряє готовий текст і без замовлення його не править. Режими:

| Режим | Що повертає |
|---|---|
| Аудит мови | Таблицю знахідок: де, цитата, пункт правил, рівень (S1 правлять із першої появи, S2 — коли скупчилось, S3 — лише в чистці), пропонована заміна |
| Чистка («почисти текст», «прибери воду») | Вичищений текст, таблицю зробленого й перевірку, що зміст не втрачено й нічого не додано |
| Аудит документа як цілого | Ще таблицю повноти, межі жанру, безпеки |
| Діагностика кальок | Таблицю підозр: слово, рід кальки, англійський оригінал, заміна, упевненість; вердикт за вами |
| Аудит ТЗ | Таблицю «рядок ТЗ · що не так · пропоноване закриття · джерело» |
| Фінальний прохід | Прохід по готовому тексту перед видачею; його вимагають письмо й вивантаження |

Факти не звіряє (це `factcheck`), рішень не оцінює (це `review`). Чистка, що
зачіпає твердження чи зміст, — уже письмо.

**Запит:** «Приберіть воду з внутрішньої нотатки. Не додавайте фактів:
"Це потужний інструмент для надзвичайно швидкої обробки журналів. Збирач читає
журнали з двох вузлів і записує їх у сховище. Період опитування — 60 с."»

> Результат чистки:
>
> > Збирач читає журнали з двох вузлів і записує їх у сховище. Період опитування — 60 с.
>
> | Цитата | Пункт | Рівень | Дія |
> |---|---|---|---|
> | «Це потужний інструмент» | 1.4, слово зі списку | S1 | Речення прибрано: «потужний інструмент» нічого не каже про систему… |
> | «надзвичайно швидкої обробки журналів» | 1.4, підсилювач замість числа | S2 | Прибрано разом із реченням. Число взяти ніде, а додавати факти заборонено |
>
> Перевірка «Переписування зберігає зміст»: втрачено лише оцінне твердження…
> Додано: нічого.
>
> Питання власнику: якщо «швидка обробка» — реальна вимога, потрібне число або
> джерело.

### Фактчекінг — `factcheck`

Звіряє твердження готового тексту з документацією вендора й джерелами
проєкту: чи правдиве воно сьогодні, для якої версії і редакції. Перевіряє
можливості, обмеження, вимоги, сумісність, версії, параметри команд; першими —
твердження зі словами «завжди», «тільки», «автоматично», «підтримується».
Повертає таблицю тверджень зі статусом, доказом, адресою джерела й наслідком
помилки. Колонку «Вердикт» заповнюєте ви. Текст не править: правка за
результатом — окрема задача письма. Виняток — покрокова інструкція, де
очевидне виправлення за джерелом скіл вносить сам і показує переліком.

**Запит:** «Виконайте фактчекінг за sources.md для умовного продукту «Ліхтар»:
"У «Ліхтарі» 2.0 максимальний розмір пакета — 100 записів. Автоматичне
повторення доступне в усіх редакціях. У редакції Pro повторення ввімкнене за
замовчуванням."»

> Перевірено 3 твердження… Підтверджено: 1. Спростовано: 2.
>
> | № | Твердження | Статус | Доказ | Наслідок | Вердикт |
> |---|---|---|---|---|---|
> | 1 | «Автоматичне повторення доступне в усіх редакціях.» | Спростовано | `sources.md`: «Автоматичне повторення є тільки у Pro; за замовчуванням вимкнене» | хибна конфігурація: розрахунок на повторення в Base не спрацює | |

>
> Колонка «Вердикт» порожня: її заповнює власник. Текст не правився.

### Вивантаження — `export`

Готує документ для читача поза командою: `.docx`, `.xlsx`, `.pdf`, лист чи
повідомлення. Прибирає із чистового тексту робочий слід (хід пошуку, робочі
блоки, внутрішні колонки), оформлює посилання, таблиці й схеми, розкриває
маркери за правилами вивантаження. Останній крок перед збіркою — повний
мовний прохід по остаточному тексту: прохід, зроблений до пізніших правок,
скіл не зараховує. Якщо вивантаження змінює зміст, це ще й письмо. Хук плагіна
зупиняє хід, у якому файл зібрано без такого проходу.

**Запит:** «Збери цей текст у файл note.docx: "# Резервне копіювання.
Резервну копію щоночі знімає скрипт backup.ps1."»

> note.docx зібрано: заголовок 1-го рівня і один абзац, рендер перевірено…
> Мовний прохід по остаточному тексту знахідок не дав…
>
> *[Хук: «У цьому ході зібрано .docx, .xlsx чи .pdf, а після останньої зміни
> тексту мовного проходу не було…»]*
>
> Хук спрацював, і формально він має рацію: `language.md` я прочитав до того,
> як записав `note.md`… Повторний прохід по остаточному тексту виконано. Текст
> не змінився, тому `note.docx` не перезбирав.
>
> `Стадії: вивантаження (export/SKILL, export; профіль вивантаження: немає) · мовний прохід по остаточному тексту, повторний після запису note.md (language: частини 1–2, Діагностика кальок, Фінальний прохід, Чек-лист мови) · збірка (.docx, pandoc…)`

### Планування — `plan`

Вмикається лише на ваше прохання («спершу план», «склади план»); сам скіл
його не пропонує. План записує постановку дослівно й критерії виконання, які
можна перевірити спостереженням. Перед повною роботою — короткий «план для
плану»: що прочитати, що витягти, на що звірити, який вигляд матиме результат
і чого не робити; на цій зупинці ви кажете «так» чи «пропускаємо». Кроки
йдуть у формі «крок · вихід · стан», і крок закривають лише доказом.
Зміну постановки під час роботи дописують дельтою, а не переписують план.
Коли ви кажете «план готовий», його перевіряє рецензія.

**Запит:** «Спершу план: треба перенести службу черги «Ліхтар» з однієї
віртуальної машини на дві, щоб вона пережила відмову вузла».

> **Постановка, дослівно:** «перенести службу черги "Ліхтар" з однієї
> віртуальної машини на дві, щоб вона пережила відмову вузла».
>
> | № | Критерій виконання (спостереження) |
> |---|---|
> | 1 | Вимкнення одного вузла не зупиняє приймання повідомлень… |
> | 2 | Після вимкнення вузла вже прийняті повідомлення не губляться… |
> | … | … |
>
> | № | Крок | Вихід | Стан |
> |---|---|---|---|
> | 2 | Розвідка | Опис нинішнього стану: тип черги, де стан, клієнти | не почато |
> | 6 | Тест відмови за критеріями 1–3 | Протокол: що вимикали, що спостерігали | не почато |
> | … | … | … | … |
>
> 1. **Що означає «вузол»: фізичний хост чи сама ВМ?** Від цього залежить, чи
>    достатньо двох ВМ: вони мусять жити на різних хостах, інакше відмова
>    хоста вб'є обидві. Рекомендація: хост…

### Рецензія — `review`

Незалежна перевірка плану чи документа кількома агентами, які не бачили
розмови, у якій цей план чи документ писали. Окремий агент-координатор вибирає вузьких
рецензентів: узгодженість, здійсненність, обсяг, опонент рішень, безпека,
експлуатація, архітектура, мережа, платформа, ємність, вимоги, схеми,
перевірка реальності. Для плану діє стеля: до п'яти рецензентів для короткого
плану, до семи — для більшого. Для документа знахідки ще перевіряє окремий
агент-опонент (чи стоїть цитата дослівно, чи не завищено вагу, чи не відоме
це вже). Великий документ координатор ділить на частини між рецензентами. Головна сесія
звіряє кожну знахідку з джерелом, відкидає хибні з поясненням і зводить звіт.
Текст не править: правка за знахідками — через письмо.

Окремий легкий режим — **тест читача**: один свіжий агент читає документ без
контексту й каже, що незрозуміло людині, яку документ називає читачем.

**Запит:** «План готовий, перевір незалежно: перенести резервне копіювання
файлового сервера з нічного скрипта backup.ps1 на Azure Backup. 1) Увімкнути
MARS-агент на сервері. 2) Налаштувати політику: щодня о 23:00, зберігати
30 днів. 3) Перший повний знімок зробити вручну. 4) Через тиждень вимкнути
backup.ps1.»

> Усі рецензенти повернулися. Кожну знахідку я звірив із текстом плану, а
> твердження про MARS перевірив на Microsoft Learn… Усі кути працюють на одній
> моделі, тому позначка «N незалежно» лише показує, скільки кутів знайшли
> проблему, і доказом не є.
>
> | № | Вага | Знахідка | Вердикт |
> |---|---|---|---|
> | 1 | блокер | Крок 4 вимикає backup.ps1 через календарний тиждень. Перед цим немає пробного відновлення, критерію успіху й відкату… | підтверджено |
> | 2 | блокер | Жоден крок не створює Recovery Services vault… Агент не «вмикають»: спочатку створюють vault, далі завантажують vault credentials… | підтверджено |
> | 3 | блокер | Не вирішено, де зберігається passphrase і хто ним володіє… | підтверджено |
> | … | … | … | … |
>
> Відкинуто як хибне: «ручний перший запуск нічого не додає». Microsoft прямо
> рекомендує запускати on-demand backup після налаштування розкладу…

Цей прогін ішов до введення стелі й запустив десять рецензентів; з поточною
стелею на такий план координатор бере п'ять.

**Запит (тест читача):** «Тест читача для інструкції runbook.md. Читач —
черговий адміністратор, який цю службу бачить уперше». В інструкції чотири
кроки: зупинити службу командою, «очистити тимчасову теку, як зазвичай»,
запустити службу, «переконатися, що все працює».

> **Висновок.** За цією інструкцією черговий адміністратор, який бачить службу
> вперше, не виконає перезапуск. З 8 питань документ відповідає на одне:
> команду зупинки.
>
> | № | Питання читача | Цитата | Чому проблема | Що замість |
> |---|---|---|---|---|
> | 2 | Яку теку чистити і як? | «Очистіть тимчасову теку, як зазвичай» | «Як зазвичай» посилається на усну практику, шляху немає | Повний шлях і точна команда |
> | 4 | Як зрозуміти, що все працює? | «Переконайтеся, що все працює» | Критерію немає | Команда перевірки й очікуваний результат |
> | 8 | Як відкотитися? | відсутнє | Очищення теки може бути незворотним | Відкат або пряме «відкату немає» |
> | … | … | … | … | … |
>
> **Межа тесту.** Він перевіряє зрозумілість, а не істину.

### ukrainian-fiction

Диспетчер і шість скілів: `write`, `scene`, `ideas`, `audit`, `reader`, `setup`. Правила конкретної
книги пакет не тримає: їх дає профіль книги (канон голосу, еталонні уривки,
словник, канон фактів). Профілю немає — скіл каже, чого бракує, і не вигадує. Сюжет, повороти
й поведінку героїв вирішує автор: скіл пропонує варіанти з механізмом і
наслідком, а не готовий абзац замість питання. Доручити будову ШІ автор може
лише сам: явним запитом і підтвердженням, на одну сцену.

| Функція | Що робить |
|---|---|
| Будова (`scene`) | Розбір чи план сцени, епізоду, глави на рівні сюжету |
| Ідеї сцен (`ideas`) | Коли задуму ще немає: кілька ідей сцени чи повороту з механізмом, наслідком і ризиком, далі розвиток вибраної в діалозі з автором до каркаса. Режим задає профіль книги; режим «повністю на ШІ» вмикається лише явним запитом і підтвердженням автора |
| Письмо (`write`) | Нова сцена чи правка наявної за голосом книги; перед письмом — еталонні уривки й кінець попередньої глави; репліки героїв — за їхніми картками, а для вибору фраз — промпт, який автор сам запускає в різних моделях |
| Аудит готового тексту (`audit`) | Таблиця знахідок із пунктом правил, варіантом і впевненістю; що правити, вирішує автор. «Почисти» — аудит із мовною правкою |
| Діагностика кальок (`audit`) | Таблиця підозр із нормою; нічого не править |
| Тест читача (`reader`) | Як текст прочитає людина без контексту: агент-читач отримує лише текст глави; де профіль книги дозволяє, главу паралельно читає модель OpenAI; сам не вмикається, нічого не править |
| Налаштування (`setup`) | Майстер покроково заводить профіль книги й картки героїв за шаблоном; перевіряє наявну картку й нічого в ній не править |

**Запит:** «Чи звучить це як ШІ? "Вона відчула, як серце пропустило удар. Він
дивився на неї, і в його очах була суміш страху та надії. Співпадіння? Навряд
чи."»

> | № | Пункт | Де | Що не так | Варіант | Впевненість |
> |---|---|---|---|---|---|
> | 1 | Р4, кліше · Р6 | «серце пропустило удар» | Готовий образ; почуття подано тілом, як найчастіше робить модель | Що вона зробила, коли злякалася? Або просто «злякалася» | висока |
> | 2 | Л7 | «суміш страху та надії» | Обгортка-абстракція, до того ж парна | Лишити одне почуття, показати його дією | висока |
> | 3 | Л8 | «Вона відчула, як» | Слово-фільтр між читачем і подією | Прибрати фільтр | висока |
> | 5 | К1 | «Співпадіння» | Калька з російської | «Збіг» | висока |

Повний приклад — [docs/examples.md](docs/examples.md).

## Чим відрізняється

- **Питає, а не вигадує.** Чого бракує в тексті (числа, назви, деталі сцени),
  те стає питанням до автора, а не правдоподібною вставкою.
- **Зміст важливіший за стиль.** Після чистки скіл звіряє результат з
  оригіналом: чи не зникли факт, умова, обмеження, маркер невизначеності.
- **Вага ознак.** Не кожна ознака — дефект: одні правляться з першої появи,
  інші лише тоді, коли скупчилися. Так скіл не вичищає живий авторський текст.
- **Кальки — окремим проходом.** Таблиця підозр із нормою та впевненістю,
  вердикт за автором. Спірні пари звірено зі словниками.
- **Крок не губиться.** Кожен скіл закінчує роботу рядком стадій — переліком
  файлів, які справді прочитано. Пропущена стадія видна в рядку. Якщо в ході
  зібрано .docx, .xlsx чи .pdf без мовного проходу по остаточному тексту, хук
  плагіна зупиняє хід і вимагає цей прохід.
- **Два жанри — два плагіни.** Технічний текст і художня проза мають різні
  правила: розмовна репліка героя чи свідомий повтор у прозі — прийом, а не вада.

## Як перевіряється

Набори тестів лежать у [tests/](tests/). Для технічного плагіна — 24 синтетичні
випадки: мовна правка й аудит, джерела й фактчекінг, жанри й вивантаження,
а також тексти, які правити не треба. Для художнього — 6 людських уривків,
які скіл не має «виправляти». Критерії записано до першого прогону,
виконавець їх не бачить.

Скіл позначив те, що вадою не є? Відкрийте issue за шаблоном «Хибне
спрацювання»: підтверджений випадок стає контрприкладом у самому правилі.

### Claude Desktop і claude.ai

Відкрийте чат (не вкладку Code), далі «Персоналізація» (Customize) → Плагіни →
«Додати» → додати маркетплейс, у поле URL — `alexgorby/claude-skills` або
`https://github.com/alexgorby/claude-skills`. Після цього обидва плагіни
з'являться на вкладці «Огляд», кнопка «Додати» ставить потрібний.

Додавати маркетплейс треба із чату. Маркетплейс, доданий із чату, лежить в обліковому
записі claude.ai, і плагін видно в чаті, Claude Code і Cowork (де він є). Доданий, коли
активна вкладка Code, ляже лише на цей комп'ютер і в чаті його не буде.

Плагін оновлюють вручну через меню: Плагіни → «⋮» біля плагіна → перевірити оновлення → «Оновити».

Під час додавання чи оновлення технічного плагіна Claude Desktop попереджає,
що плагін «містить компоненти, які виконують код». Йдеться про хук
`hooks/check_language_pass.py`. Наприкінці кожного ходу хук читає журнал
поточної сесії. Якщо в ході зібрано `.docx`, `.xlsx` чи `.pdf`, а після
останньої зміни тексту мовного проходу не було, хук повертає Claude вимогу
виконати мовний прохід. Інакше він нічого не робить. Файлів хук не змінює, до
мережі не звертається. Хук запускають командою `python`, тож Python має бути
в `PATH`.

Агенти рецензії і хук мовного проходу працюють і в Claude Code, і в чаті
Claude Desktop: так показала перевірка 02.11.2026, хоча таблиця сумісності в
документації Anthropic для чату пише «ігнорується». Чат claude.ai у браузері
окремо не перевіряли.

Інший шлях — завантажити скіли архівами: «Персоналізація» → Skills → додати
власний скіл. Архіви збирає `pwsh ./build.ps1` у теку `dist/`: для технічного пакета —
сім архівів, по одному на скіл, кожен зі своєю копією спільних правил. Архіви не
містять агентів і хука: рецензія йде без субагентів, а про мовний прохід перед
вивантаженням нагадує лише рядок стадій. Завантаження архівів не перевіряли:
стаття підтримки claude.ai називає межу опису скіла в 200 знаків, а описи скілів
пакета довші. Не тримайте одночасно плагін й архівну копію того самого скіла:
Claude бачитиме два однакові скіли.

## Джерела

Правила написано наново українською. Ідеї частково взято з досліджень і чужих
скілів; англомовні правила перенесено лише там, де вони працюють для української.
Повний перелік із посиланнями — у `SOURCES.md` технічного плагіна (для рецензії —
ще розділ «Джерела» в `skills/review/SKILL.md`) і в розділі «Джерела пакета»
у `SKILL.md` художнього скіла.
