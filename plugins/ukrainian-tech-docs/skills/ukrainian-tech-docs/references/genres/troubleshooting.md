# Troubleshooting — запис випадку

Кожен випадок описується однаково, і симптом стоїть першим: інженер шукає
за симптомом, бо причини ще не знає.

Постмортем — окремий жанр (`postmortem.md`): він закриває інцидент, а цей запис
допомагає наступному інженерові розпізнати й полагодити той самий випадок.

| Крок | Що в ньому |
|---|---|
| Симптом | Точний текст помилки, ID події, код. Очищений від ідентифікаторів замовника, але придатний для пошуку копіюванням |
| Свідчення | Що саме спостерігали: вивід команди, запис у логу, стан у порталі |
| Причина | Підтверджена або ймовірна — **розділяти явно** |
| Безпечна дія | Спочатку діагностика, що нічого не змінює. Потім дія, що змінює стан, з попередженням перед нею |
| Перевірка | Чим підтверджується, що полагодили |
| Умова ескалації | За якої ознаки припиняються самостійні спроби й до кого йдуть |

Заголовок документа — симптом або назва проблеми. Рядки помилок мають бути такими,
щоб їх можна було скопіювати з логу й знайти пошуком.

**Причина пишеться тільки перевірена.** «Ймовірна» означає: є свідчення, що на неї
вказують, і вони названі. Зв'язок, якого ніхто не перевіряв, у запис не йде
навіть із маркером (`evidence.md`, розд. 4).

Наслідок для архітектури, моніторингу чи процедур у запис не вбудовується: він іде
посиланням на документ, який через цей випадок змінено.

## Чек-лист Troubleshooting

- [ ] Симптом стоїть першим і придатний для пошуку копіюванням
- [ ] Підтверджена й імовірна причина розділені явно
- [ ] Діагностика, що нічого не змінює, стоїть перед дією, що змінює стан
- [ ] Перед дією, що змінює стан, є попередження
- [ ] Є перевірка й умова ескалації з адресатом
- [ ] Немає ідентифікаторів замовника
