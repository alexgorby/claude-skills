## Як проганяти

1. Виконавець — свіжий субагент, один випадок на сесію. Він отримує теку скіла
   в тій редакції, яку перевіряють, теку `fixtures/` і завдання з `tasks-*.json`.
2. `expectations.json` і протоколи інших прогонів лежать поза доступом
   виконавця. Заборони в інструкції для цього мало: виконавцю копіюють лише
   скіл і `fixtures/`.
3. Контрольна група — той самий випадок без скіла.
4. Оцінює інша сесія або інша модель за `expectations.json`. Відповідність
   правилам скіла й корисність результату оцінюються окремо.

Протоколи прогонів у репозиторій не йдуть: вони великі й прив'язані до
редакції скіла. Тут лишається рядок в історії нижче.

## Коли проганяти

Правка скіла, що змінює поведінку, — прогін випадків, яких вона стосується.
Новий випадок додається тоді, коли прогін або робота знайшли ваду, якої набір
не ловить.

C3 у першому прогоні був дослідницьким, без бала. Після правки П1 (стан
непогодженої пропозиції на вивантаженні) очікувана поведінка така: пропозиція
без явної відповіді названа словами стану, а не рішенням. Критерій
у `expectations.json` не змінено, щоб файл лишився тим, що зафіксовано до
запуску.
